# Architecture write-up

The schema treats organization membership as the source of authorization truth. Nhost Auth only establishes identity (`x-hasura-user-id`) and the normal authenticated Hasura role (`user`). Application roles live in `org_members`, because the same user can be an owner in one organization and a viewer in another. Every user-facing select/mutation permission reaches the current resource's organization and requires a matching membership row. As a result, knowing a workflow/run/step UUID from another tenant does not help: the row permission resolves to false before the row is returned or changed. `workflow_runs` redundantly stores `org_id` to make execution queries and tenant filtering inexpensive, while the foreign-key path back to `workflows` remains the canonical relationship.

Layer 2 is intentionally different from ordinary tenant CRUD. `workflow_steps` insert/update/delete permissions permit owners and editors generally, but privileged `db_write` and `notify` rows require an owner membership. `workflow_triggers` applies the same owner-only rule to `webhook`. This is enforced in Hasura metadata, so bypassing the React UI with hand-written GraphQL still fails. Approval cannot be modeled only as a table update permission: it is a transition in a running state machine. The `approveStep` Action loads the target step/run with an admin backend request, checks that the caller is owner/editor in exactly that run's organization and that the target is an unresolved `approval_gate`, then calls `approve_step_and_enqueue`. That Postgres function repeats the authorization check under row locks, marks the gate approved once, moves the run from `paused` to `queued`, and creates a resume job atomically.

Runs are durable rather than tied to the lifetime of the initial Action HTTP request. `triggerWorkflowRun` checks membership and reserves quota atomically with `reserve_org_quota`, creates a `workflow_run`, and inserts a `run_job`. A Hasura Event Trigger invokes the executor for the job. This lets the Action return the run ID immediately; the frontend can subscribe to `step_runs` while execution proceeds. The executor claims each job once, resumes from `cursor_position`, writes `step_runs` before/during/after each node, retries `llm_call` and `http_request` once, and saves `execution_context` after each step. At an approval gate it writes `awaiting_approval`, advances the cursor, marks the run `paused`, and exits. The approval Action queues a new job, so the same executor resumes from the next step instead of replaying completed work.

Quota admission is concurrency-safe. `organizations` stores used and reserved slots. `reserve_org_quota` resets the monthly window when needed and increments `quota_reserved` only if `quota_used + quota_reserved < quota_limit`. A paused run keeps its reservation. Successful completion atomically converts the reservation to usage; failure releases it. `organization_usage_current_period` exposes an org-level aggregate view for the UI.

Trigger paths converge on the same start helper. Manual runs use the authenticated Action. Webhook runs use a public Hasura Action whose handler validates an owner-created SHA-256 webhook secret before selecting a fixed workflow. A cron trigger calls a scheduled dispatcher once per minute and starts matching `scheduled` workflow triggers with dedupe keys. Inserts into `watched_events` fire a Hasura Event Trigger that starts matching `database_event` workflow triggers. `notify` follows the same event-driven pattern: the executor only writes `notification_outbox`; a separate Event Trigger delivers Slack/email/log notifications. This avoids coupling workflow state to third-party notification latency.


All Hasura-to-Function webhooks are authenticated with Nhost's generated `NHOST_WEBHOOK_SECRET`: metadata injects it as the `nhost-webhook-secret` header and each Function compares it in constant time before processing Action session variables or event payloads. This prevents direct calls to public Function URLs from fabricating Hasura-originated requests. Retried side-effecting steps are also made as idempotent as the target allows: `db_write` and notification outbox rows have per-run/per-step unique constraints, while non-GET HTTP requests receive a stable `Idempotency-Key`. Workflow definitions are soft-archived on edit so historical `step_runs` keep valid foreign keys and remain auditable.
